## 3. ObjectStore 接口与状态机

冻结端口（与 ports.json 精确一致）：

```java
ObjectRef stage(ActorContext, byte[] bytes, String expectedHash, long size);
ObjectRef commitReference(ActorContext, ObjectRef, Ownership.ArtifactRef);
String   authorizeDownload(ActorContext, ObjectRef);   // 5 分钟签名 URL
```

- 公共 `ObjectRef` 严格实现冻结 schema `$defs/ObjectRef`：`key/hash/size/mime/encrypted`，不新增字段。对象 key 为服务端生成的随机 UUID，不可猜测、不经客户端路径/原始文件名。
- 内部状态（不进入公共 DTO）由 `StoredObject` 承载：`status`（`STAGING/COMMITTED/DELETED`）、`schemaVersion`（元数据格式版本，供跨版本演进）、`createdAt/committedAt`。hash 为 SHA-256（复用 `CanonicalRequest.digest`），size 为字节数，mime 由服务端按 magic bytes 检测（非扩展名）。

状态机：`stage` 写入 `STAGING` → `commitReference` 校验并登记 `COMMITTED`（完成标记在事务提交后、幂等）→ `authorizeDownload` 仅对 `COMMITTED` 发放签名 URL → 孤儿清理只删超 TTL 且无引用无 hold 的对象。

## 4. 暂存→校验→引用提交→完成标记协议

严格实现 `stage → hash/size verify → DB reference commit → mark complete`：

1. `stage`：服务端重新计算 SHA-256 与字节数，`expectedHash`/`size` 与实算不符即 `422 HASH_MISMATCH/SIZE_MISMATCH`；空对象 `422 EMPTY_OBJECT`；超限 `422 OBJECT_TOO_LARGE`（默认 64 MiB，域任务在其上再加 1 MiB/20 MiB 限制）。写入用临时文件 + 原子 rename，半文件永不可读。
2. `commitReference`：在调用方事务内执行 `Ownership.require(actor, articleId, artifact, newCommit=true)`（同文章、同 Owner、非 stale、hash 匹配），再校验对象存在与 hash/size，随后**登记 `markCommitted` 到事务的 afterCommit**（有事务时）或立即执行（无事务时）。`markCommitted` 幂等：已 COMMITTED 直接返回。
3. 失败语义：对象写成功但 DB 事务失败 → 对象留在 `STAGING`、无 `OBJECT_COMMITTED` 审计、不返回业务成功（AC-29）；DB 提交成功但完成标记失败 → 对象 `STAGING` 且已引用，清理任务会**治愈**（把已引用的 STAGING 改标 COMMITTED）而非删除，可重试幂等；重复提交/进程中断不产生错误引用或错误成功。

## 5. 受权下载

`authorizeDownload` 顺序：`ObjectRefRegistry.resolve(key)` 解析对象 → 所属文章 → `Ownership.requireArticle(actor, articleId)` 校验 Owner → `revoked` 拒绝 → 校验对象 `COMMITTED`（否则 `409 OBJECT_NOT_READY`）→ 发放 5 分钟签名 URL → 审计 `OBJECT_DOWNLOADED`（仅记录对象 UUID、Owner、actor、trace、结果与 hash，不记正文/签名/密钥）。

- 另一 Owner、匿名、伪造 actor、跨文章引用、已撤销、未知对象均被拒绝（跨 Owner 隐藏为 404）。
- 对象 ID 不可猜测不代替权限检查；签名 URL 默认 5 分钟，过期需重新授权；不写前端 localStorage。
- Local 签名 URL 用 HMAC-SHA256 绑定 `(key, expiry)`；S3 用 SigV4 presign（`X-Amz-Expires=300`）。密钥仅在服务端内存派生，绝不入日志/响应。

## 6. 孤儿清理、删除与保留

`cleanupOrphans(dryRun)`：仅删除同时满足「超 24h TTL」且「无任何当前/历史引用」且「无 hold」的 `STAGING` 对象；已引用对象改标 COMMITTED（治愈）；hold/保留/未超期对象保留。删除前用 `ObjectRefRegistry` 再次核对引用，不依赖客户端传入状态；不使用宽泛 CASCADE、目录全删或全桶扫描（S3 仅列 `objects/` 前缀）。支持 dry-run 影响统计，供 T37 接入恢复/保留。无任何引用注册表时**失败关闭**（不删也不治愈，全部保留）。

归档（`archivedAt`，T06）与明确删除（T37 retention 顺序解除引用）区分；T04 的 `delete` 只删单个对象，不冒充归档。

## 7. Local 与 S3 适配器

**Local**：配置私有目录（POSIX 下目录 0700、文件 0600，Windows 为 no-op）；对象/元数据以 UUID 为 key 隔离，不经静态 Web 根或可猜测路径；PUT/GET/HEAD/删除；写入临时文件 + 原子移动；读取前校验状态、hash、大小。拒绝路径遍历、绝对路径、盘符、反斜杠、NUL、编码绕过（`ObjectKeys.requireValid` 窄白名单，仅接受规范小写 UUID）。

**S3 兼容**：私有桶、PUT/GET/HEAD/删除、hash/size/mime/status 元数据（`x-amz-meta-*`）、5 分钟 SigV4 presign。endpoint/bucket/region/凭证仅来自服务端配置；不落日志/响应的密钥、签名、Authorization、内部 endpoint、供应商完整错误。能力缺失（未配置）→ `FEATURE_NOT_READY`（503），不伪造成功；签名失败/不存在/超时/重试分别映射。不假定各 S3 兼容服务支持同一版本锁定/批量删除/强一致性。**S3 适配器为纯 JDK 实现（`java.net.http` + 手写 SigV4），未引入 AWS SDK，故未改 pom.xml**；真实 MinIO/AWS 网络联调是待集成项（见 §12）。

## 8. 安全边界

T04 负责对象 key、路径、下载授权与存储权限。SafeFetch 的完整 SSRF 防护归 T15；本任务不提供绕过 SafeFetch 的下载入口——`authorizeDownload` 只对已提交对象发签名 URL，不把任意外部 URL 当可信对象地址。图片 magic/MIME/像素/重编码归图片任务；T04 只保存并返回真实 size/hash/mime（magic 检测，非扩展名）。
