### 2.1 F2-01（P2）：model 级 provider 配额为什么曾经无声失效

**根因（读代码所得，与派发的描述一致）**：`BudgetPolicyConfig.quotas()` 把属性名去掉 `editorial.cost.provider-quota.` 前缀后，取"最后一个点之前的原文"当 map 键——于是 `…provider-quota.openai.gpt-5.max-concurrent` 存成 `openai.gpt-5`；而 `BudgetPolicy.providerQuota()` 查的是 `provider + "|" + model`，即 `openai|gpt-5`。两种拼法永不相交，所以 model 级条目**配了也查不到**，返回 `Optional.empty()`，`BudgetService.checkProviderQuota()` 紧接着 `if (quota == null) return;` 直接放行——写侧拼法、读侧拼法、javadoc 教的 `provider_model` 三种各不一样，最后一种没有任何一条路径可达，结果是 fail-open。

**为什么上一轮的反向控制抓不到它**：18 条减弱全部打在"数字被改、守卫被关、镜像替换生产适配器、断言被掏空"上，**没有一条动 scope 的拼法**；而测试两侧各自看是对的——配置路径唯一的配额用例只写了 provider 一级（`provider-quota.mock.max-concurrent`），单段键两种拼法恰好相同（`mock` == `mock`），所以它也过；model 一级只在 `budgetPolicyCeilings` 里用测试手搓的 `Map.of("mock|mock-model", …)` 断言读侧，绕过了写侧。两侧都不缺断言，中间缺的是"同一条路径从配置走到读侧"的用例，静态检查也从不比较两侧拼法——门不存在，所以看不见。

**修法（四处统一到一种拼法）**：

1. `BudgetPolicy.scope(provider, model)` 成为**唯一**的 scope 定义（provider 级 = `provider`，model 级 = `provider|model`）；`quotas()` 与 `providerQuota()`/`quotaScope()` 都必须经过它，`verify.py` 第 11 项断言全模块只有这一处 `provider + "|" + model` 拼接。
2. `quotas()` 把属性路径翻译成 scope：段数必须是 2（`<provider>.<leaf>`）或 3（`<provider>.<model>.<leaf>`），更长或未知叶名一律 `INVALID_PROVIDER_QUOTA_KEY`；`provider`/`model` 段不得含点，保留名 `unconfigured` 不得当 provider 用。
3. `BudgetPolicy` 构造期校验已存的键：出现带 `.` 的键直接 `INVALID_PROVIDER_QUOTA_KEY`——这正是旧写侧产出的形状，所以将来任何第二套拼法在装配时就炸，而不是静默变成不生效的上限。
4. 取消"缺即不限"：一个 scope 必须同时写 `max-concurrent` 与 `calls-per-day`，缺任一条报 503 `QUOTA_NOT_CONFIGURED`；`Integer.MAX_VALUE`/`Long.MAX_VALUE` 的填空从代码里删除。
5. provider 完全没条目时的语义改由**必需键** `editorial.cost.provider-quota.unconfigured`（`unlimited` / `refuse`）声明，没有回退值，缺失即 503 `QUOTA_NOT_CONFIGURED`；选 `refuse` 时服务在扣预算前报 503 `PROVIDER_QUOTA_NOT_CONFIGURED` 且不写任何行。"我们忘了写"不再是"这一侧不设限"。
6. 顺带修掉同一族的另一个静默错误：provider 级条目过去在 `owner+provider+model+day` 窗口上度量，等于把一条 provider 上限按 model 数量放大；现在窗口跟着条目层级走——`provider|model` 量该 model，`provider` 量该 provider 的全部 model。
7. 文档/注释同步：javadoc 里 `[_<model>]` 的教法删除，键名一律 `.max-concurrent` / `.calls-per-day`（F2-05 的报告笔误也按此订正）。

**新增证据**：`modelLevelQuotaReachesTheLookupThatReadsIt`（真配置装配 → scope → 读侧，含四种坏写法各自的拒绝）、`modelAndProviderQuotaScopesEachBindTheirWindow`（服务路径上 model 覆盖先命中、provider 级跨 model 累加到 3 才拒）、`unlistedProviderFollowsTheStatedQuotaPolicy`（refuse 与 unlimited 两种声明的实际行为）。静态门新增第 11 项，反向对照新增 9 条（写侧退回点号、读侧自己拼、缺省回填 MAX_VALUE、必需 switch 长出默认值、refuse 分支被删、provider 级窗口退回按 model、`BudgetPolicy` 不再拒绝畸形键的对应减弱、报告把叶名写错、以及 F2-02 的诱饵），总数从 18 条到 27 条。

### 2.2 追问：真实 YAML 绑定路径（复审方点出的本轮最关键漏洞）

我上一版自己标注的未证明项是关键：**用例喂的是扁平 `MockEnvironment` 键名**，而生产写的是嵌套 YAML。若绑定出来的键名不是 `quotas()` 期望的形状，新逻辑照样静默不命中，测试却永远绿——与 F2-01 同一种病。现在这条已从"未证明"变成"已证明"：

- **机制**：`CostPricingTest.yaml(String)` 与 `T08PostgresTest.nestedYamlQuotaIsEnforcedByTheService` 用 `org.springframework.boot.env.YamlPropertySourceLoader` + `ByteArrayResource` 加载**真实嵌套 YAML 文本块**，把返回的 `PropertySource` 加进环境后交给 `BudgetPolicyConfig.from(env)`。可用性不是假设：先用 `jar tf`/`javap` 确认离线仓库里 `spring-boot-3.5.16.jar` 有 `load(String, Resource)`、`snakeyaml` 在位，再由 `mvn test-compile` 通过验证（在 `.work` 副本里跑，未碰 `backend/target`）。
- **绑定结果与实现是否一致（第 1 步的实测答案）**：我在 `.work/yamlprobe` 用真实 Spring 跑了一遍探测，输出为 `editorial.cost.provider-quota.openai.gpt-5.max-concurrent` 这类"嵌套键按点连接、模型名单独成段"的平铺名，与 `quotas()` 期望的 2/3 段形状**一致**，所以没有实现需要按绑定结果修改；探测同时确认属性源是 `OriginTrackedMapPropertySource`（属于 `EnumerablePropertySource`），正是 `quotas()` 遍历的那一类。
- **行为断言**（不是键名相等）：活库用例从该文档装配出 `mock-provider.max-concurrent=3` 与 `mock-provider.mock-gpt.max-concurrent=1`（键名就是该夹具的 `PROVIDER`/`MODEL` 常量，写错会当场 503，本轮第一次跑就是这样暴露的），交给真实 `BudgetService`：该 model 第二笔 429 `PROVIDER_QUOTA_EXCEEDED`；provider 级的 3 跨 model 累加（1+2 放行，再一笔拒）；文档写的 `unconfigured: refuse` 让未列出的 provider 直接 503 `PROVIDER_QUOTA_NOT_CONFIGURED` 且不落账本行（三次拒后仍 `holds()==3`）。
- **形状变体必须响亮失败**（同一用例逐条断言）：camel 叶名 `maxConcurrency` → `INVALID_PROVIDER_QUOTA_KEY`（探测显示 `Environment.getProperty` 不做 camel→kebab 反向规范化，枚举到的原始键名保持 `maxConcurrency`，因此这是"未知叶名"而不是"未配置"）；四段路径 `mock.mock-model.beta.<leaf>` → `INVALID_PROVIDER_QUOTA_KEY`；含点的模型名 `gpt-5.1` 被 YAML 展平成第四段 → `INVALID_PROVIDER_QUOTA_KEY`；只写一条叶值 → `QUOTA_NOT_CONFIGURED`；文档完全不写 `unconfigured` → `QUOTA_NOT_CONFIGURED`。
- **保留字 `unconfigured` 的取舍（复审方自查项）**：它确实与 provider 名共用一棵子树。保留它的理由是"配额相关的东西都在一起，且不需要新前缀"；代价是碰撞必须响亮：`provider-quota.unconfigured.max-concurrent`（把保留字当 provider 用）在 `quotas()` 里当场 `INVALID_PROVIDER_QUOTA_KEY` **拒绝启动**，既不静默当开关也不静默忽略；`BudgetPolicyConfig.UNCONFIGURED_LEAF` 的 javadoc 已写明该保留字与两条拒绝路径，YAML 与扁平两种写法都有断言覆盖。若你更希望彻底不同命名空间（例如 `editorial.cost.unconfigured-provider-quota`），那是一行改动，但会破坏"配额都在一棵子树里"的可读性，我按最小侵入保留现状。

- **两种 scope 同时存在时的优先级（复审方自查项）**：**model 级覆盖先命中并只量该 model；provider 级条目量该 provider 的全部 model；两者都没有条目才轮到 `unconfigured` 开关**。这条语义由 `BudgetPolicy.quotaScope()`（先精确 `provider|model`，回退 `provider`）+ `BudgetService.ceilings()` 里跟着应答级别选择的窗口实现，并由两条活库用例钉住：`modelAndProviderQuotaScopesEachBindTheirWindow`（provider=3 与 model=1 并存时，第二个同 model 预占被 model 条目拒掉，而 provider 级还余 2）与 `nestedYamlQuotaIsEnforcedByTheService`（同一文档两级并存，实测优先级的两端）。
- **门的加强**：`verify.py` 第 11 项现在还要求这两条用例**各方法体内**都有嵌套文档（provider 级两叶 + model 级两叶）并真的经由 loader / `BudgetPolicyConfig.from(env)` 喂给服务；反向对照新增 3 条：文档换成点号平铺键 → 红；活库用例改回手搓策略（不再 `from(env)`）→ 红；"保留字不得当 provider"的分支删掉 → 红。反向对照 27 → 30 条。

### 2.3 F2-02 / F2-05：门与文档自己的两处漏洞

- **F2-02**：`verify.py` 第 10 项原先用 `function.find("FOR UPDATE")` 判断锁是否在聚合之前——函数里任何一处提到 `FOR UPDATE` 的注释都能冒充它。现在改成锚定真实 SQL：必须匹配到 `SELECT budget_limit INTO limit_amount FROM editorial.article_job WHERE id=NEW.article_id FOR UPDATE;` 这条语句本体，用该匹配的 `lock.start()` 与占用聚合的位置比较，函数体内任何不属于这条语句的 `FOR UPDATE` 文本都算诱饵并判失败，同时要求锁之后紧跟 `IF NOT FOUND` 缺失文章守卫。反向对照加了专门一条把真锁移到聚合之后、并在前面留一句 `-- FOR UPDATE ...` 诱饵：旧写法会绿，新写法红（另有"诱饵顶掉锁"一条）。

## 3. 数据库迁移现状与权限

- `tests/engineering/T08/migration-draft.sql` 保留为**评审基线**（首行仍标注 DRAFT）；主 agent 已把它的正文安装为 `backend/src/main/resources/db/migration/V5__cost_ledger_pricing.sql`，只替换头 3 行注释。`verify.py` 把这件事做成机器断言：去掉各自头 3 行后正文必须**逐字节**相等——实测两边都是无 BOM 的 LF，正文各 13,119B、CR 字节 0 个（上一轮报告写的"V5 为 CRLF/12,947B/173 CR"在主 agent 重写文件后已不成立，因此这里不再对换行符做归一化：一旦有任何一方改行尾或偷改正文，检查项立刻失败）。本轮为修 F-02 给触发器加锁时两边同步改动，改完后仍逐字节相等。
- 同一项还断言版本化文件恰为 V1–V5（无第六个）、V5 只创建 `cost_ledger` 与 `cost_pricing_version`、且没有其它版本化文件涉及 cost 表。
- **runner 不再手套草案**：`run_pg.py` 直接按 Flyway 顺序应用 `beforeMigrate__t02_function_defaults.sql` → V1…V5 → `R__t02_function_permissions.sql`、`R__t02_schema_permissions.sql`，与正式迁移路径一致。
- 并发：服务路径上所有金额上限判定按 scope key 排序获取事务级 advisory lock（ARTICLE / DAY / PROVIDER|MODEL / CLAIM / SLOT），避免跨作用域死锁；结算对 reservationId 单独加锁并用 `status + lock_version` 乐观谓词更新，竞争输者 409，不覆盖赢家。advisory lock 的键是 `sha256(scope)` 前 16 位十六进制转 long（`shared/CanonicalRequest`），数据库自己算不出来，所以触发器不能靠它——数据库侧改用行锁。
- 数据库规则：BEFORE-INSERT 上限触发器 `cost_ledger_admit` 只做**文章预算**这一条：先 `SELECT budget_limit FROM editorial.article_job WHERE id=NEW.article_id FOR UPDATE` 锁文章行，再聚合占用（`occupied+NEW.amount>limit_amount` → 23514）。加这把锁之前实测是漏的：同一篇文章剩最后 1 单位时，两个绕过服务、直接 INSERT 的并发事务在 READ COMMITTED 旧快照上各自看到 `occupied=0`，**两边都通过**（2 行、占用 2.0 USD 超预算），运行 #1 的 `concurrentBypassWritersCannotOversubscribe` 因此失败（`expected: <1> but was: <2>`，见第 5 节）；加锁后两个事务被行锁串起来，恰好一个提交、另一个 23514，占用 1.000000、1 行。日预算、次数上限、Provider 配额不在任何可锁的行里，因此触发器不复述它们，注释也不再声称复述。其余守卫：BEFORE UPDATE/DELETE 的 `cost_ledger_guard`（账本不可删除、事实不可改、预估金额与身份不可变、必须逐 revision 递增、状态机限制）；DEFERRABLE 一致性触发器 `cost_ledger_consistent`（RESERVED 不得有事实、UNKNOWN 必须有未解决事实且无终态事实、终态恰好一个终态事实且头行镜像与该事实金额一致；对账后保留的 UNKNOWN 事实不参与终态镜像比较，这是本地集群实跑出来的必要修正）。
- 权限：默认不授权。显式 `GRANT SELECT,INSERT,UPDATE ON editorial.cost_ledger`、`GRANT SELECT ON editorial.cost_pricing_version` 给 `editorial_runtime`，无 DELETE/TRUNCATE、无价格写权限；三个触发器函数 `REVOKE ALL FROM PUBLIC`。V5 应用后的实测授权：`editorial_runtime = INSERT/SELECT/SELECT/UPDATE`（对 cost 两表）加 `audit_log` 的 SELECT/INSERT，`editorial_migrator` 保留 owner 全权限。
